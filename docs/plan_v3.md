# 我們要做什麼

## 摘要

一個讓你不用碰電腦就能控制電腦的裝置。手勢控制 + 語音下指令，全部在本地跑。

用延遲把它分成兩層：**反射層**（毫秒，板子做手勢）和**認知層**（秒，LLM 做語音）。

---

## 場景

下廚的時候，手是髒的、濕的、拿著東西的。

- 食譜滑到下一步 → 現在要洗手、擦手、碰螢幕、再洗手
- 想查「這個食材可以換成什麼」→ 手機在旁邊但碰不得
- 視訊電話進來 → 同上

**這是一個真的很煩、每個煮過飯的人都遇過的問題。**

現有的解法是語音助理，但廚房很吵——抽油煙機、水聲、油爆聲——語音辨識常常失敗，而且「往下滑一點」這種連續控制用講的很不精準。

**手勢適合精準的即時控制，語音適合複雜的查詢。兩個一起用。**

下廚只是切入場景。我們做的是**系統層級的控制**，所以同一套東西在任何需要「手不方便」的情況都能用——實驗室、維修、簡報、健身。

---

## 核心想法：反射層 vs 認知層

**反射層**：視覺模型直接觸發動作，不經過 LLM。
- 比手勢 → 立刻捲動 / 暫停 / 移動游標
- 延遲毫秒級，**只有 edge AI 做得到**

**認知層**：LLM 聽、想、組合動作。
- 「幫我查這個可以用什麼代替」→ 自己組出搜尋網址並開啟
- 「設五分鐘計時器」→ 呼叫工具
- 延遲幾秒，可接受

**這兩層的分法跟人很像**：手碰到燙的東西會先縮手，才意識到痛。

---

## 為什麼 Edge 是必要的（這次論證更強）

原本「手勢晚 200ms 觸發」其實還可以忍。但加了**游標控制**之後不一樣了：

**游標晚 200ms，人會立刻覺得這東西壞了。** 手眼協調的回饋迴路對延遲極度敏感，這是知覺層級的硬限制，不是體驗偏好。

而且游標要**每一幀都更新**（30-60 FPS），這是持續的高頻推論，不是偶爾觸發。雲端方案在這裡根本不成立。

板子上那顆 NPU 是必要的——沒有它，模型跑 CPU 會慢 17 倍（文曄工作坊實測），游標會變成幻燈片。

**而且影像不上雲端**——這是有人在家裡活動的畫面，本地處理是前提不是加分。

---

## 控制設計：混合模式

不要只選一種，兩個都要。

### 離散手勢（主力，90% 的情況）

只做 3-4 個，不用記太多：
- 上滑 / 下滑
- 暫停 / 播放
- 進入游標模式

快、不累、穩定。

### 游標模式（萬用逃生口）

- 比特定手勢進入
- 游標跟著手移動
- 換手勢 = 左鍵 / 右鍵
- 放下手或超時 = 退出

**為什麼需要它**：快捷鍵要記，學習成本高。游標不用記任何東西，看到什麼點什麼。而且它證明了**通用性**——不是只能做預設好的幾個動作。

**為什麼不能只有它**：手舉久了會酸（gorilla arm，Kinect 時代的教訓），而且廚房情境下精準點擊其實很煩。

**額外好處**：「進入/退出模式」順便解決了誤觸發——不在游標模式時，你切菜的手不會亂動游標。

## PC 控制：只用跟畫面位置無關的原語

**絕對不要用 `pyautogui.click(x, y)`。** 解析度、視窗位置、字體縮放一變就全壞。demo 當天接投影機解析度改變，直接爆炸。

```python
# 安全
pyautogui.scroll(-300)
pyautogui.hotkey('ctrl', 't')
pyautogui.press('playpause')
pyautogui.write("雞胸肉 食譜")
webbrowser.open("https://...")
subprocess.run(["notepad"])

# 危險 — 不要
pyautogui.click(847, 392)
```

幾乎所有功能都能用快捷鍵或 URL 達成。開 Google 查詢就是 `webbrowser.open("https://google.com/search?q=" + query)`。

**例外**：游標模式本身會用到 `pyautogui.moveTo()`，但那是相對於螢幕解析度動態計算的，不是寫死座標。

## LLM 的工具（通用原語，不是功能專用）

```python
def scroll(amount: int)
def press_hotkey(keys: list[str])
def open_url(url: str)
def launch_app(name: str)
def type_text(text: str)
def get_screen_context() -> str      # 現在開著什麼視窗
```

**不為每個功能寫一個工具，讓 LLM 自己組合原語。** 這才是真正的 agentic。

### 讓 LLM 知道螢幕上是什麼

盲目控制會出錯。最低成本解法是抓視窗標題：

```python
import pygetwindow as gw
active = gw.getActiveWindow().title   # "雞胸肉料理 - Google Chrome"
```

一行就讓 LLM 知道現在在幹嘛，不用截圖、不用 VLM。**投報率極高，一定要做。**

## 做的順序

**主線優先，游標模式最後做。** 游標的調校很吃時間（濾波參數、映射範圍、點擊凍結），效果好壞又很主觀，容易掉進調參地獄。別讓它排擠主線。

1. **手部模型上板，量幀率**（最大風險，見下方）
2. **離散手勢 + 防誤觸**：攝影機固定，先確認幾個手勢分得出來
3. **LLM function calling**：電腦上測，給假工具，看判斷準不準
4. **PC 控制原語**：確認 pyautogui 在你們的系統上都能動
5. **游標模式**（加分項，做不出來不影響主 demo）

## Demo 腳本

用**真的食譜網站**，不要自己做網頁——自己做的話評審會覺得「你只是做了一個支援手勢的網頁」，技術貢獻消失了。

1. **手勢捲動食譜**（30秒）— 基本控制
2. **「幫我查這個可以用什麼代替」**（30秒）— LLM 自己開 Google 搜尋
3. **「設五分鐘計時器」**（20秒）— 開計時器
4. **切換到完全不同的軟體**（20秒）— 音樂播放器 / 視訊會議，手勢一樣能用
   → **這步證明這不是為某個網站客製的，是通用輸入方式**
5. **游標模式**（30秒）— 展示可以點任何東西
6. **NPU 對照**（20秒）— 切到 CPU，游標變幻燈片

# 技術細節與坑

## 1. MoveNet 做不了手勢（最大問題，今天就測）

MoveNet 是**全身 17 點**，手部只有「手腕」一個點。分不出你比幾根手指。

選項：
- **找 MediaPipe Hands 的 TFLite 版**，自己做 Vela 編譯。沒人保證跑得動，**要最優先驗證**
- **只用手臂大動作**（MoveNet 就夠）：手往上抬 = 上滑、往下 = 下滑、舉過頭 = 進游標模式。精細度低但零風險
- **自己訓練小型手勢分類器**：資料要自己收

**建議：先用手臂大動作把整套流程跑通**，確定能動之後行有餘力再換手部模型。

**注意**：游標模式其實只需要「手腕位置」，MoveNet 就夠。點擊手勢才需要手部模型——如果手部模型跑不動，點擊可以用「手停留 1 秒」代替（dwell click）。

## 2. 游標抖動：必須做濾波

單點關鍵點的定位誤差正常就有好幾像素，直接映射游標會瘋狂抖。

**用 One Euro Filter**，不要自己寫簡單移動平均。它的特性是：慢速移動時大幅平滑（精準定位不抖），快速移動時少平滑（大動作不延遲）。網路上有現成 Python 實作。

## 3. 游標映射方式

**建議絕對映射，但只取畫面中央約 40% 區域對應整個螢幕。** 這樣手不用揮很大，解析度換算也比較好。

相對映射（像觸控板）精度更好但不直覺，先不做。

## 4. 點擊時游標會漂移

**最惱人的問題**：比出點擊手勢的瞬間手一定會微動，游標跑掉，點到隔壁。

**解法：點擊觸發時凍結游標位置**，用前幾幀的平均座標，不是當下座標。

## 5. 怎麼知道你在比手勢還是在切菜

下廚時手一直在動，很容易誤判。

**建議「停留確認 + 特定區域」組合**：手勢要舉到胸口以上、維持約 0.5 秒才觸發。切菜的手不會這樣。

**這件事要留時間調參數。**

## 6. 手勢重複觸發

MoveNet 每秒十幾幀，比一個手勢持續一秒 = 觸發十幾次。

```python
COOLDOWN = 1.5  # 秒，離散手勢用
# 連續手勢（捲動）不用冷卻，但要限制單次幅度
```

## 7. 使用者怎麼知道手勢有被收到

手是髒的、可能沒在看螢幕。沒反應的話你會一直重複比。

- **聲音回饋（最重要）**：短提示音，不用看螢幕
- 畫面：手勢圖示閃一下
- 雲台點頭

**很容易忘記做，但實際使用超重要。**

## 8. 廚房噪音會殺死語音辨識

抽油煙機 + 水聲 + 油爆聲，Whisper 會失準。

- **建議用耳麥或領夾麥**，離嘴近，訊噪比高很多
- 或 demo 時不開抽油煙機，但要誠實說明

## 9. 攝影機位置

- 太高：手在流理台上會被身體擋住
- 太低：被鍋具擋到、沾油
- **建議斜上方側邊 45 度**，避開正上方（蒸氣）和正前方（被身體擋）

**Demo 前要固定好位置並實測過。**

## 10. 距離和視野

C270 視角約 60 度，人站流理台前約 1-1.5 公尺。

**要實測**：這個距離下手在畫面裡佔多少像素？夠辨識嗎？
如果太小，考慮裁切畫面中央區域再送進模型。

## 11. 雲台要不要保留

廚房情境下追蹤價值降低（人站在流理台前不太移動）。

**建議保留但簡化**：單軸，主要當回饋（收到手勢時點頭）和「它在看著你」的存在感。因為它是現場感染力的來源，而且反射層需要一個實體輸出。

## 12. Demo 時評審會想自己試

- 手勢設計成左右手都能用
- 準備簡單的「教學卡」給評審看要比什麼
- 主 demo 由練過的組員操作，最後再開放評審試

## 其他會卡的地方

- 蒸氣會糊鏡頭 → 離爐子遠一點，或 demo 時不開火
- C270 自動白平衡會讓顏色飄 → 關掉，固定參數
- 廚房光線不均（櫥櫃陰影）→ 固定曝光，必要時補光
- 舵機噪音干擾麥克風 → 用耳麥，或轉動時暫停收音
